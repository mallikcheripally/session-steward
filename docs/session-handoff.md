# Desktop handoff implementation

The browser inspector prepares a local archive for the other provider's desktop coding interface. The normal path has one Session Steward action; the destination composer still requires Send, and Claude asks the user to confirm a linked folder. Neither app is controlled through UI automation by the package.

## Data flow

1. An authenticated local POST selects one provider, session and target desktop app. The recorded project is used by default; a missing project requires its current local path.
2. `createSessionHandoff` reads semantic events and classification from the existing provider parser. Its internal `onRecord` sink receives every source record with awaited backpressure, independent of the inspector's 1000-event limit. The normal timeline API stays bounded and unchanged for callers that do not use the sink.
3. Text, structured plans, file-change references, commands, tool inputs and recorded outputs are rendered as historical evidence. Unknown, malformed, oversized and omitted media records are reported. Internal reasoning and native execution state are not transferred.
4. History chunks are capped at 64 KiB. Their index is streamed into pages of at most 100 entries. The entry file contains recent-task context and navigation instructions, not the complete index or an AI-generated summary. The most recent eight event excerpts are separately bounded.
5. A UUID-named staging directory is renamed only after the archive is complete. Source identity and before/after file information are checked. Cancellation or an exception removes the unfinished staging directory. A process crash can leave an explicitly `.preparing-` directory, which is never used as a ready handoff.
6. The inspector always shows Handoff to Claude or Handoff to Codex, with an outlined copy icon beside it. Its tooltip says Copy handoff prompt and briefly confirms Copied after copying. The Handoff action prepares or reuses the archive and requests OS dispatch to the destination URI directly. The copy icon uses the authenticated `/api/handoffs/prepare` route, which never dispatches an app, and copies the prepared message. A distinct route prevents an older server from silently treating copying as a launch request. Both controls keep their names after preparation. Partial archives include their coverage notes in the destination message and START.md; they do not add a review step in Session Steward. App-opening failure retains the archive and its copyable prompt.
7. The browser records completed archives in a persistent SQLite catalog. Before preparing another snapshot, the exporter checks the source fingerprint and verifies every existing archive file's identity and metadata. An unchanged archive can be reused for either destination; its creation date stays fixed and its last-handoff time updates. Changed or missing files force a fresh export. A source change during verification prevents reuse.

## Storage and limits

Files live in `.session-steward-handoffs/<uuid>/` inside the selected project so the receiving local agent can read them. A local `*` ignore file keeps all contents out of normal Git status without editing repository or global ignore settings. Linked output folders and unexpected existing ignore files are refused. On POSIX, directories/files are private to the current user. The original transcript, provider databases and session metadata are never written by the exporter.

Completed archives persist until removed in **Handoffs** or manually; they are not managed by provider session cleanup. Automatic archive deletion is off. No model calls, account login, dependency installation or cloud uploads occur during export. Reading the archive in a receiving agent uses that app normally.

The small `handoffs.sqlite` catalog holds paths, session identifiers/titles, source fingerprints, byte counts, creation/last-handoff dates, and archive identity. It lives in per-user application data, outside the installed npm package: macOS `~/Library/Application Support/session-steward`, Windows `%LOCALAPPDATA%/session-steward`, Linux `$XDG_DATA_HOME/session-steward` or `~/.local/share/session-steward`. An explicitly supplied server configuration directory isolates the catalog there instead. The catalog has no transcript body and does not back up the project-local files. Removing a project or running `git clean -xfd` can remove its archives. No data belongs in an npm installation or temporary `npx` directory.

Project-local storage keeps history available within the receiving agent's selected workspace. Claude can be configured to [block reads outside working directories](https://code.claude.com/docs/en/settings), so a central archive outside the project would introduce another access boundary. This choice also keeps unrelated projects' transcript bodies separate. The central catalog provides management across projects without scanning every project on each request.

## Archive management

The session inspector has one toolbar below its title and labels. Handoff and copy stay visible beside the Keep session toggle and Actions menu; there are no permanent explanatory paragraphs for each feature. Keyboard-accessible tooltips explain quick actions, and menu items explain workspace-wide effects. Existing Keep confirmations and Undo remain shared with the rest of the browser. If a workspace already keeps the session, its kept control opens the protection actions instead of silently removing the broader rule.

Incomplete exports show a compact Partial handoff warning beside the actions, with a warning icon and explicit dismissal. Coverage warnings remain visible until dismissed because they affect the context transferred; they are also retained in the archive and destination prompt. Copy success is confirmed briefly on the copy icon. Starting another preparation clears the previous result and shows any new coverage warnings again.

View handoffs is session-specific: `/handoffs?providerId=<provider>&sessionId=<id>` carries an exact source identity into catalog queries. A compound SQLite index supports scoped counts, pagination, age/search filters and sorting without loading every archive. The active session filter is visible and removable; the top Handoffs navigation clears it. Missing or invalid scope parts are rejected, and the frontend refuses an unscoped response from an older server. No native provider scan is needed to filter handoffs.

The **Handoffs** view pages the catalog (25 records by default, maximum 100), with project/session search, last-handoff age, size sorting, cross-page selection up to 100, and an explicit deletion confirmation. Last-handoff time is not last-read time; there is no inference that an archive is unused. Deleting breaks future reads by conversations referencing that archive. Source transcripts, provider databases, and project code stay intact.

Only registered UUID folders directly within a recognized project handoff root can be deleted. Cleanup checks canonical workspace, folder ownership, directory identity, and manifest identity before atomically renaming a selected archive to `.deleting-<uuid>`. Partial removal retains a retryable catalog record; a restart between marking and renaming is also recoverable. Nested links are removed without following them. Unexpected replacement folders are refused. The catalog uses its own SQLite database and a cleanup lock, not provider database snapshots.

Missing projects or archives can have only their listing removed. **Find handoffs** scans one explicitly chosen current project, registers recognized earlier archives, and reconnects moved projects. Discovery streams directory entries in batches of 100 with a time check between entries; it never searches the whole computer. Earlier format-1 handoff archives are recognized without expanding provider transcript support. Manually deleted catalog data can be rebuilt this way. Incomplete `.preparing-` exports are not treated as completed archives.

The source limit is 4 GiB, output limit twice the source budget, and preparation time limit five minutes. The browser serializes handoff preparation with its other file mutations. A disconnected/cancelled request aborts preparation before app dispatch. External provider writers are not locked: detected source changes make the result partial. Index data is streamed, not retained as a full-history array.

Only the selected session is transferred. Linked chats, repository files, binaries and running processes are not automatically included. The receiving agent is instructed to check current project files, branch and chronological corrections before acting. A Markdown archive is context for a new conversation, not native session migration.

## Desktop links

- ChatGPT: `codex://new?path=<absolute-project>&prompt=<short-message>` ([official documentation](https://learn.chatgpt.com/docs/app/commands)).
- Claude Code in Claude Desktop: `claude://code/new?folder=<absolute-project>&q=<short-message>` ([official documentation](https://support.claude.com/en/articles/14729294-open-claude-desktop-with-a-link)). Folder confirmation is enforced by Claude. No CLI login is needed.

URLs are encoded with `URLSearchParams`. OS dispatch uses `open`, `xdg-open`, or Windows `rundll32.exe` without a command shell. Exit status only reports dispatch; it cannot establish that a particular app version populated its composer. The copy action remains available for missing or older handlers. No automatic Send or folder-confirmation bypass is attempted.

The copy action starts its clipboard write inside the click gesture and supplies promised text data where supported, preserving the activation required by [WebKit's clipboard implementation](https://webkit.org/blog/10855/async-clipboard-api/). A denied clipboard write leaves the prepared prompt available for manual copying.

## Verification boundaries

Unit and HTTP tests cover complete and partial exports, old/current fixture layouts, source identity, unchanged source files, long histories, tool evidence, malformed and oversized input, missing workspaces, output links, cancellation, ignore rules, and missing desktop handlers. Catalog tests cover persistence, reuse/invalidation, project separation, selected deletion, interrupted cleanup, replaced directories, missing entries, moved projects and earlier archive discovery. `npm run benchmark:handoff` measures fresh workers at approximately 32 and 256 MiB including catalog registration and archive reuse, checks the entry-file budget, retained heap and peak RSS, and rejects memory growth proportional to the input size. `npm run benchmark:handoff-catalog` measures paginated queries over 50,000 synthetic archives across 25 projects with response-size, heap and latency budgets.

The browser preparation and copying flow was checked with synthetic data and an injected mock OS opener, without sending more Claude model requests. Prior [feasibility results](../experiments/handoff-feasibility/REPORT.md) include actual desktop context-retrieval trials. They do not validate an automatic OS launch, actual code continuation, every historical recipient version, or Windows/Linux GUI behavior. CI runs the unit and HTTP suite on macOS, Linux and Windows, plus Linux scale benchmarks; those checks do not establish native GUI behavior.

Compatibility was reviewed on November 28, 2026 against [Codex CLI 0.172.0](https://github.com/openai/codex/releases/tag/rust-v0.172.0), [ChatGPT's production update feed](https://persistent.oaistatic.com/codex-app-prod/appcast.xml) (26.1120.50957), [Claude Code 2.1.332](https://github.com/anthropics/claude-code/releases/tag/v2.1.332), and Claude Desktop 6.28899.6 from its stable update feed. Codex 0.171.0 and 0.172.0 have identical state migrations; cleanup and restore regressions cover both versions. The Claude 2.1.332 fixture was recorded from the official CLI in an isolated configuration with a loopback mock response and no real credentials or model calls. Desktop checks inspect installed storage metadata and use invented records with matching shapes. Unsupported completed-item variants, malformed records and oversized lines remain visible as partial coverage; a supported storage profile is not a promise that every historical record is understood.
